# Event playbook

Detail for Steps 5 to 7 of the event-matchmaking skill: the host sheet, the messages, a
blast if asked, door mode and what to do after the event.

## Host sheet

One page, no phone numbers or emails, in this order:

1. **Door introductions:** pairs the host introduces in person: thin profiles,
   first-timers, non-members, anyone likely to hang back.
2. **Top 5 connectors:** the guests with the most strong complementary links. The host
   uses them as bridges when someone's match hasn't arrived.
3. **Backups:** guest → backup, for quick re-pairing.
4. **No match yet:** guests for the host to place on the night.

## "Find [name]" messages

- Template 15 in `message-craft.md`, filled per guest, in the manager's voice, with the
  backup named.
- Timing: 60 to 90 minutes before start, in the event's time zone. Much earlier (the day
  before, a week ahead) and plans change, matches drop out and the message is forgotten.
  If the manager wants to send early, say this once, then do what they decide.
- Over ~10 guests, don't write every message out: one template plus a fill table
  (guest, find, reason, backup, send time), the first 3 written in full as examples, and
  the rest offered in batches of 10.
- Format for the channel (`message-craft.md`, Channels). Each message goes to one guest.

## Luma blast or email to all guests

- Only if asked. It goes to everyone, so it's a broadcast and can't name anyone's match.
- Say that personal messages do better: in one ~850-member professional network, a named
  person to find drew ~37% replies against ~28% for a generic reminder.
- Draft it; never send it. The manager decides.

## Door mode

When the manager sends the names of guests who have arrived but whose match hasn't:

1. Pair each with their approved backup if the backup is there.
2. Otherwise pair them with another arrival, under the same rules: no same organisation,
   professional reasons only, no one in more than 3 introductions.
3. Reply with short lines the host can read out: "[guest] → [new match]: [reason]".

For who actually came, use check-ins: the Luma guest CSV, or Eventbrite's check-in
status (`platform-guide.md`).

## After the event

When the manager brings back replies, a check-in list or an export:

- Ledger: "met" becomes `connected` plus the outcome; "didn't meet" sets
  `didn't connect`, unless check-in shows one person never came (note that instead).
  `ledger.md`, "Event rows", has the full rules.
- A backup pair gets a ledger row only if they end up meeting.
- Anyone who wants a proper follow-up intro gets a new row with source = `request`, to be
  handled as a member introduction.
- Report: pairs made, pairs where both attended, pairs who met, replies received.
